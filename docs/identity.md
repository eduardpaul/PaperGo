# Groups, roles and module scopes

PaperGo uses one organization per database. Local authentication is the default. It signs in `admin_user` (default `admin`) with the configured password using HTTP Basic or the session cookie from `POST /auth/login`. When the password is unset and no administrator exists, an interactive start prompts for it and a non-interactive start fails. An existing password is left unchanged on later starts. For OIDC, set `ADMIN_SUBJECT` to the verified subject of the first administrator, or set `ADMIN_GROUP` (with `OIDC_GROUPS_CLAIM`) to provision an IdP group with the Administrator role. Exactly one of these is required in OIDC mode. Proxy authentication requires `ADMIN_SUBJECT` matching a proxy-verified username; profiles and groups are locally managed. Development authentication defaults `ADMIN_SUBJECT` to `DEV_SUBJECT`. Startup creates the Administrator and Member roles once. Changing the setting after initialization does not grant another subject administrator access.

Verified bearer subjects enroll with the Member role on first use. Profile claims supply the stored display name (`name`, then `preferred_username`, then subject) and email, returned in `GET /v1/identity/users` and `GET /v1/identity/me`. `GET /v1/people` returns active subject IDs. Removing a role assignment keeps it removed on subsequent authentication. Administrators can also enroll subjects through `POST /v1/identity/users` before adding them to groups or roles.

The directory lives under `/v1/identity`. `user.read`/`user.manage`, `group.read`/`group.manage` and `role.read`/`role.manage` govern their respective directory entities. Group membership uses group scopes; role assignments and the scope catalog use role scopes. User and group reads are granted to the built-in Member role. Group and role metadata changes and deletion require the current quoted integer `If-Match`. Membership and assignment PUT/DELETE operations are idempotent and address a `user` or `group` principal explicitly. Nested groups have a maximum depth of 10 and cannot contain cycles. Built-in roles are immutable. Changes cannot remove the last effective Administrator, including changes to nested group membership or group sync. Group sync retries protected removals on subsequent provider-token requests, including requests with unchanged claims, so removal takes effect once another active administrator exists.

Directory groups have a `source` (`local` or `oidc`). When `OIDC_GROUPS_CLAIM` is set, PaperGo syncs group names from the token claim (or UserInfo fallback when `OIDC_GROUPS_FROM_USERINFO=true`). Missing groups are created with `source='oidc'`. The user's memberships in OIDC groups are synchronized with the claim (at most 100 groups). Local groups are untouched by token sync. Effective profile changes, group creation and membership changes are audited in the sync transaction; an audit failure rolls back synchronization. Unchanged identities and deferred membership removals do not emit change audits. Direct membership changes on OIDC groups through `/v1/identity` return 409 `group_managed_by_identity_provider`. OIDC groups can be nested inside local groups and receive roles and ACL grants like any group.

Role scopes are additive and resolve through direct assignments and nested group membership. `GET /v1/identity/me` returns the caller's subject, profile, synced groups, and effective scopes. `GET /v1/identity/me/scopes` shows the caller's current effective scopes. The Member role grants `workspace.read`, `workspace.create`, `list.read`, `list.write`, `contentType.read` and `taxonomy.read`. Organization administrators receive every catalog scope. Role and membership changes take effect without restarting the server or obtaining another token.

Content authorization combines module scopes and resource ACLs inside the database transaction. Workspace owners retain ACL control but still need the relevant module scope. `workspace.manage` is the explicit organization-wide ACL override; it does not grant other module scopes implicitly. Copying an ACL preserves group IDs, and copying workspace inheritance preserves dynamic workspace roles. REST, WebDAV and workflow item actions all use current persisted role and group membership.

Taxonomy roles operate on one organization term store shared by every workspace. `taxonomy.read` permits reads and open-set/keyword contributions without workspace membership. `taxonomy.manage` permits curation, imports, promotion, usage counts and organization taxonomy audit access. These scopes do not grant workspace or content access.

Users have an `active` flag. GET `/v1/identity/users/{subject}/status` requires `user.read`; PUT with `{"active":false}` or `{"active":true}` requires `user.manage`. Inactive users receive no module scopes, cannot authenticate into module operations and are excluded from active-user selection. Enrollment preserves activation status. Disabling the last active administrator is rejected and rolled back. Person fields and GET `/v1/people` use these active subjects; person selection requires `list.read` and grants no content access.

Active users read and edit their own [preferences](preferences.md) at `/v1/identity/me/preferences`. Personal values inherit the live organization defaults and built-in settings. `/v1/organization/preferences` reads the defaults; changes require `organization.manage`, which administrators have and can delegate through roles. Preference access does not require directory read/manage scopes.

File downloads require `document.read`; file creation, replacement and restoration require `document.write`, in addition to list scopes and item ACLs. A role with `list.write` and no `document.write` can edit metadata while file replacement is denied. WebDAV applies document scopes to its reads and writes as well.

User profiles store `display_name` and `email`. Administrators create, read and edit profiles at `/v1/identity/users` and `/v1/identity/users/{subject}`; user.read and user.manage control reads and writes. The list contains active users. `/v1/identity/me` returns the current profile and effective scopes; PATCH permits display-name changes only. Display names allow 200 Unicode characters and email addresses allow 256 bytes.

DELETE `/v1/identity/users/{subject}` anonymizes the profile to “Deleted user”, removes email, disables authentication, removes identity memberships and assignments, personal preferences, content grants and WebDAV credentials. The stable subject remains so author and person values still resolve. Self deletion, deletion of the last active administrator and deletion of the last active workspace owner are rejected. Transfer workspace ownership first. Deleted accounts cannot be reactivated or enrolled again with that subject. REST and WebDAV admission reject inactive users.

`GET /v1/organization` exposes the deployment’s stable organization ID, identifier, display name, description and version to every active user. The initial identifier/name are `papergo`/`PaperGo`. PATCH requires organization.manage and the organization ETag; it changes profile metadata while retaining the ID. Current-user profiles include organization_id and organization_identifier. This is one organization per deployment.

In bearer-authenticated deployments, personal REST tokens are managed at `/v1/identity/me/tokens` (GET/POST) and `/v1/identity/me/tokens/{id}` (DELETE). Create with `name`, a nonempty list of distinct `scopes`, and optional `expires_in_days` (1–3650, default 90). At most 100 active tokens may exist per user. Creation returns `token` metadata and a `secret` once. The database stores a SHA-256 hash of the random 256-bit secret. Lists expose a prefix, scopes, creation/expiry times and last-use time.

Send personal tokens as `Authorization: Bearer {secret}` to the REST API. Personal-token requests preserve the stored profile and group memberships; identity-provider tokens supply profile and group synchronization. Every permission check intersects token scopes with the user’s current roles; removing a role takes effect immediately. A token can create another token only within its own current scope set. Expired, revoked, inactive-user and deleted-user tokens fail authentication. Revocation requires ownership. Account deletion removes all REST tokens. WebDAV retains its separately issued credentials in bearer-authenticated deployments. Proxy authentication instead uses the proxy’s HTTPS Basic credentials; personal-token and WebDAV credential endpoints return 404.

Deleting an account permanently purges its personal Home and documents, metadata histories, configuration and execution payloads in the same transaction as account anonymization. Shared library documents and organization audit records remain. Personal Home does not block the last-workspace-owner guard; shared workspaces still do. Removed file objects are queued for retryable cleanup, preserving bytes referenced by surviving documents. Home and Inbox bindings are included in core configuration/content packages.

Home cleanup includes DBOS replay inputs and outputs when the runner is attached. Permanent audit markers prevent in-flight or replayed runs from recreating removed execution payloads.

## Integration access tokens

Organization managers use Administration → Access tokens or `GET/POST /v1/identity/tokens` and `DELETE /v1/identity/tokens/{id}`. The list contains organization-wide personal and integration token metadata, including identity, issuer, expiration, revocation and last-use time; it never returns a secret or its hash. Administrators can revoke either kind.

Creating an integration token accepts `name`, distinct `scopes` held by the issuer and optional `expires_in_days` (default 90, 1–3650, or 0 for Never). It atomically creates a separate service identity, returns the random `pgo_` secret once and stores only its hash. Service identities cannot sign in through OIDC/proxy identity assertions or issue personal tokens. Their scopes come from their active integration credential, including when queued work reconstructs its credential ID. Disabling or deleting the service identity, expiration or revocation blocks the credential immediately; resource ACLs still apply. Add the service identity to the appropriate workspaces or ACLs. The explicit `workspace.manage` scope grants organization-wide content access.

Send `Authorization: Bearer pgo_…` over HTTPS. Integration bearer authentication is available in bearer and proxy deployments. A proxy ingress for integration clients must forward this Authorization header to the API; a separate API hostname can do so without an NPM Access List, while PaperGo validates every request. The sample’s browser hostname uses its NPM Basic Access List and therefore expects browser credentials. Keep PaperGo’s backend ports unpublished and route the API hostname through the trusted proxy network. Personal tokens remain available only in bearer deployments.
