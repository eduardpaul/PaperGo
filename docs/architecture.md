# DMS / CMS foundation

## Deployment boundary

One organization owns one deployment, SQLite database, and blob directory. A workspace is an organizational content scope within that deployment. No tenant ID is inferred from an HTTP header. Verified OIDC subjects or authenticated trusted-proxy assertions enroll in a persisted organization directory; typed user/group principals, nested groups and module-scoped roles feed service authorization and SQL read predicates. Multi-organization SaaS and cross-deployment identities require explicit future design.

## Authoritative content and derived reads

`resources` holds immutable identity and container membership, plus hierarchy, permissions inheritance, lock version, and revision pointers. An item belongs to exactly one list or library, including when nested in a folder; folders and items move only within that collection, never below themselves, which triggers enforce. The resource's name/keywords/values cache represents head content; it is never used as a reader's published representation. In libraries, the case-folded head name of each live folder and item (`name_key`) is unique per parent, so the library can be presented as a file system.

Deleting an item or empty folder sets its `deleted_at` in one transaction. REST folder deletion with `recursive=true` and WebDAV folder deletion remove the entire live tree atomically, requiring write access to every descendant. Ordinary REST deletion rejects populated folders, including when a child is unreadable. Workspace and collection deletion tombstone their entire live resource trees and disable and tombstone bound workflows. Deleted entries retain content for collection recycle-bin recovery. Manager purge removes content, snapshots, publications and grants while retaining audit/run identifiers and durably queuing storage cleanup. Deletion removes the derived surfaces and field indexes, which hides deleted items from search, queries and relationship visibility; it retains relationships hidden until their endpoints are active and readable, emits an item deletion event for each affected item, and `authorize` treats a tombstone as missing. Permissions, preconditions, cleanup and events commit or roll back together.

`schema_revisions` freezes the collection's shared field catalog and content types, including each type's field membership and cross-field rules. Field keys, types and decimal scales are stable identities; labels and validation options evolve through new schema revisions. Organization content types reference organization field IDs; collection attachments hold their default selection. Shared definition changes advance every attached collection schema atomically. Items have immutable assignments to an attached content type. `item_revisions` stores complete name, keywords, exact JSON payload, content type and schema references, and optional blob reference. Revisions are append-only and database triggers prevent update/delete. Publishing selects an existing revision and never revalidates old content against a newer schema.

The item schema endpoint follows the same visibility rules as content and returns its paired immutable schema. Revision history requires ordinary item read permission and list.read scope, and includes all retained metadata revisions, including unpublished revisions. History includes schema snapshots, so consumers can interpret historical field labels and options without access to collection management.

`item_surfaces` projects the head and published revisions. Normalized keyword tables and typed `field_values` are derived from these surfaces in the same transaction; the [search index](search.md), a separate SQLite file, is derived from them asynchronously by the `search.index` workflow. A reader with ordinary read permission uses published; draft readers/editors use head by default. Collections without publishing publish every write, so head and published are always the same revision: their items and folders keep only the published surface, which every head read uses, and content is written and indexed once. Turning publishing on copies each published surface to a head surface; turning it off publishes the heads and drops the head surfaces. Index configuration can change independently of the immutable content. Projections retain historical field types/scales and use current index flags only when compatible. Index changes are tracked `operations` that rebuild one field's rows a batch per write transaction, never holding the single SQLite writer for a whole collection; a field is queryable only once its `index_status` is `ready`. Optional null values have no index row.

Indexes are opt-in to bound write amplification. Typed equality/range queries are scoped to a collection and fixed operators; neither arbitrary SQL nor JSON paths are accepted. Integer values and fixed-scale decimal units use signed 64-bit storage. Number and currency fields use exact System.Decimal-domain JSON numbers and fixed-width text ordering keys, preserving their 96-bit coefficient and scale 0..28 domain without float conversion. Decimal content is represented as a canonical string, so its precision survives HTTP serialization and history reads.

Smart folders store private or shared query definitions separately from resources. A bounded collection scan and batched catalogs feed SQL UNION branches over selected content surfaces; a taxonomy CTE matches descendants through materialized term paths (one index range per subtree), terms merged into them, and field values. Navigation groups and authorized counts use the same SQL pipeline. Packages resolve target taxonomy leaves and ancestors in batches, and import/classification writes use the transaction and item validation pipeline. See [smart folders](smart-folders.md) for ownership, limits and routes.

## Transactions and concurrency

One service instance serializes writes for the SQLite deployment. Authorization, lock checks, revision allocation, pointers, projections, publication events and audit entries commit together. Failed writes roll back all database effects. `If-Match` uses a resource lock version; content revision numbers and blob revision numbers have separate lifecycles. Publish/unpublish and permission changes consume lock versions without creating content revisions.

Reads bind authorization, publication visibility, page selection and hydration to one SQLite snapshot. Authorization uses the nearest exclusive permission scope, with workspace owners retaining control of all descendants. [Workspace memberships](workspaces.md) supply the initial scope. New resources inherit; local grants require breaking inheritance. Grants within a scope are additive, and resetting inheritance removes local grants. Break/copy/reset changes, and moves of inheriting resources, affect inherited descendants immediately while nested exclusive scopes remain independent. SQL predicates filter both resource and relationship endpoints before LIMIT. This avoids hidden candidates producing empty pages or revealing IDs through cursors. Collections allow 64 nested folders, excluding workspace and collection levels; leaf items can sit below the 64th folder. Moves validate the entire live subtree.

The chosen publishing policy belongs to the collection. Automatic mode immediately publishes each content change. Explicit mode retains the previous published revision while editors change head. Unpublish removes the published projection, retaining immutable content and lifecycle events. Policy changes require manage access; switching to automatic mode publishes existing heads in one transaction.

Blob bytes are written through the storage port before the database transaction. Metadata pins immutable object keys; failures clean up newly staged objects. A crash between object persistence and metadata commit can leave an orphan, so production reconciliation needs a grace period. This is the only cross-system transaction gap in the current local storage path.

## Search stores

The [search index](search.md) sits behind `internal/search.Store`. The default `sqlitestore` owns a separate SQLite database. The optional `zvecstore` owns native source records, FTS and HNSW indexes through cgo SDKs; it uses no SQLite search implementation. Both consume the same asynchronous indexing/content workflows and use the same query-time authorization. zvec permits one process per directory and requires offline native backups and backend copies. Search schemas belong to their DAL storage implementations.

## WebDAV

`internal/webdav` presents each WebDAV-enabled library as a file system at `/webdav/{libraryID}/`. It is a protocol adapter only: the `dms` library-file operations resolve paths, authorize, and commit each PUT, MKCOL, MOVE and DELETE as one transaction, reusing the same create, update, blob-attach and delete code as REST. A new file's first revision already holds its blob. MOVE with overwrite deletes the destination and moves the source atomically. COPY reads the source and writes new entries, so a recursive copy is not one transaction.

Paths resolve by the caller's visible names, using head names for draft readers and published names for others. Head names are unique per folder, but an unpublished rename can leave a reader seeing a published name that equals a sibling's. Then the owner of that head name wins, else the lowest ID, and listings and path resolution apply the same rule. OIDC deployments authenticate clients with API bearer tokens or access tokens (`access_tokens`, stored as SHA-256) via Bearer or HTTP Basic. Trusted-proxy deployments validate the forwarding peer and secret, then use the proxy-verified username for both REST and WebDAV. PaperGo never trusts client-supplied identity headers or forwarded client addresses. Write locks live in process memory, which matches the single-writer deployment; a shared lock store must precede multiple replicas.

## Relationships and extensions

Relationships connect items across workspaces. A link may reference a directed or symmetric relationship type or use an untyped scalar property bag. Types define validated scalar attributes and optional directional cardinality; edge mutations use their own concurrency version. They are live edges with their own audit events. Both endpoints must be readable and have a visible content surface to appear in a query. Publishing an item does not publish its linked target or freeze its relationship graph. A future release requiring reproducible relationship graphs should add immutable relationship revisions and published-edge projections explicitly.

Keep HTTP decoding/authentication in `internal/httpapi` (compiled modules add their routes through `httpapi.Module`, behind the same authentication, limits and error mapping, and each route must appear in `api/openapi.json`), the WebDAV protocol in `internal/webdav`, business invariants in `internal/dms`, workflow definitions, matching and interpretation in `internal/workflow`, durable execution in `internal/runner` (the only package that imports the engine), database initialization/migration checks in `internal/dal/database`, text recognition behind `internal/ocr.Engine`, embedding models behind `internal/ai.Embedder` (`internal/onnx` is the only package that loads ONNX Runtime, for OCR and local embeddings), the search index behind `internal/search.Store`, and object persistence behind `internal/storage.Store`. SQL and query construction belong to `internal/dal`, with Bob repositories exposing typed operations and filters to business logic.

## Workflows

Everything that happens after a change or on a schedule is a [workflow](workflows.md): triggers, a condition in the query filter language, and a flow of activity nodes, stored as immutable versions that workspace managers can change, including the built-in workflows PaperGo ships. Item writes append domain events to `domain_events` in their own transaction, so an event exists exactly when its change committed, and the write does nothing more. The runner's dispatcher, on whichever node claims the events, matches them to workflows and queues the runs, which any node's workers execute. Each node is one exactly-once step that writes through `dms` as the version's author, so permissions, validation, revisions, audit and events stay in one place. New behaviour that reacts to changes is added as an activity and, when people should see or change it, a built-in workflow, never as a hidden reaction in `dms`.

The DAL maintains SQLite and PostgreSQL masters and verifies cross-table invariants in repository transactions. Add a shared object store before introducing multiple API replicas. Group expansion, background projection workers and external search should follow measured workloads; any asynchronous projection must retain authorization checks at query time and define its consistency contract.

## Schema and verification

The complete schemas live in `internal/dal/schema/sqlite.sql` and `internal/dal/schema/postgres.sql`, edited in place; there are no development upgrade paths or compatibility layers (see [AGENTS.md](../AGENTS.md)). Each resource stores its nearest exclusive permission scope (`scope_id`), maintained by DAL transactions, so authorization uses an indexed lookup.

Tests apply that schema file. Coverage includes ownership and move constraints, permission-scope maintenance, nested group and role revocation, deletion tombstones, WebDAV protocol behavior and locking, exact values through REST, head/published search and blobs, typed index rebuilds, schema/history immutability, authorized pagination, and concurrent optimistic updates. Concurrent-client load testing, restoration exercises, quotas and idempotency keys beyond operation requests, malware scanning and observability exports remain deployment/application work.

## Application configuration

Workspace-owned schema templates and relationship types use workspace authorization. The organization term store is initialized independently of workspaces; taxonomy.read permits vocabulary reads/open contributions, and taxonomy.manage permits curation, independently of resource ACLs. Organization audit records omit workspace/resource ownership. Term merge events notify every live workspace subscription. Collection-owned views and content types use collection authorization. Applying a template explicitly adopts its checked fields and rules into a selected content type and one immutable effective schema revision; existing content is never rewritten. Rich field options and defaults are retained in those snapshots. Multiplicity and reference scope are field identity, with ordered multi-value indexes for each visible surface. Active-field deletion removes catalog membership and derived indexes while keeping frozen history.

`business_keys` reserves normalized scalar values from both live surfaces with a unique `(container_id,field_key,value)` constraint. Claims are replaced within the same transaction as revision/surface writes and removed with unpublication or deletion. Administrative uniqueness changes rebuild claims in bounded batches and roll back on collisions. Collections without unique fields skip claim work on content writes.

The bounded query specification compiles typed predicates, visible-surface sort keys, opt-in totals, and group counts into parameterized SQL. Single-key collection query pages are driven by the sort column's index (`field_values` for custom fields, `item_surfaces` for system fields) with row-value keyset seeks; `auto` merges an ordered head scan for draft readers with an ordered published scan for everyone else. Multi-key pages order the authorized matching set and seek lexicographically across exact typed ranks, with missing values last at every key. Ad hoc selection projects custom values during SQL hydration. Authorization happens before aggregation and pagination. Query selection and hydration share a snapshot; cursors bind caller, schema, collection, surface, and query. Saved views grant no access. [API behavior and examples](application-foundation.md) describe these contracts.

List [integrations](list-integrations.md) use generic encrypted JSON configuration and opaque provider state. Generic external-item bindings record ownership and managed-field keys, and immutable provider JSON data is pinned to core item revisions. Item resources and their derived surfaces have no provider-specific columns.
