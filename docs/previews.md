# File previews

The default **Generate file previews** system workflow fills the `file.preview` role in each workspace. It runs asynchronously on `file.added` and `file.updated`, and supports manual single-item runs. Workspace managers can configure the role through the ordinary built-in workflow controls.

`file.preview` renders page one of PDFs and TIFFs, or a static JPEG, PNG or WebP image, into a WebP with a longest side of at most 800 pixels and fewer than 100,000 bytes. It starts at quality 75, lowers quality and then dimensions when necessary, and never enlarges an image. Pixel limits apply before image allocation. Invalid, animated, protected or unreadable inputs produce an unavailable state. Rendering needs no OCR. PDF previews use the configured PDFium reader. Preview work has a separate one-slot worker per node, so occupied OCR/workflow work slots do not starve it.

The workflow pins its source while processing. Successful renditions are shared by source SHA-256 and a concurrent success wins over a failed render. The rendition does not replace the original, change item versions or trigger file processing again. A replacement gets its own rendition; retained or published files keep theirs. Failed renditions can be retried by a manual workflow run. The blob store holds rendition bytes and the database pins their metadata. Cleanup removes them after no unreclaimed source file holds those bytes. Workspace/organization packages and administrative backups preserve generated previews and remap their storage objects on import.

`GET /v1/items/{id}/preview` requires `list.read`, `document.read` and access to the item. It resolves the caller’s visible file before reading the shared rendition, so readers cannot inspect an unpublished replacement or another item’s preview. Optional `blob_id` follows the same retained-file permissions as content downloads. Ready responses are `image/webp` with an ETag and `X-Preview-Blob-ID`; pending responses are HTTP 202 with `status: "pending"`, the selected `blob_id` and `Retry-After: 2`. A failed render returns JSON with `status: "unavailable"`. Original file bytes are never sent by this route.

Gallery/board cards, the item Content tab and workflow selection thumbnails use this endpoint. Pending previews show a non-blocking “Generating preview…” placeholder and poll while work is pending. File replacements invalidate the rendition request. The Content tab’s **Download original** action explicitly retrieves source bytes.
