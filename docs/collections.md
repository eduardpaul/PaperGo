# Collections

Lists and libraries are collections. Workspace owners create them with `POST /v1/resources/{workspace_id}/children`. Collection managers update or delete them at `/v1/resources/{id}` using the current ETag in `If-Match`.

For safe item/folder creation retries, supply an optional non-empty UUID in `id`. The first create returns 201; a repeated create in the same collection returns the current readable live entry unchanged with 200, its Location and current ETag. Request content on a retry does not update the item. Retrying requires `item.write` module scope and read access to the existing entry; it adds no revisions, audit events or domain events. IDs belonging to a different collection, deleted content or inaccessible entries return 409 without exposing content. Collections/workspaces use server-generated IDs.

Collection names are trimmed and limited to 200 UTF-16 code units. Descriptions are limited to 2000. Both creation and PATCH accept `description` and `allow_folders`. Folder creation is enabled by default. Disabling it prevents new folders at every depth; existing folders and their contents remain usable.

Deleting a collection removes its live content and indexes and hides relationships, including descendants with exclusive ACLs. Revisions, publications and audit records remain retained history. Workflows bound to the collection or with a trigger targeting it are disabled and deleted. Tombstones are hidden by ordinary reads. Items and folders deleted inside live collections support [recycle-bin recovery and permanent purge](recycle-bin.md).

Item and folder PATCH merges supplied custom-value keys into current metadata. Omitted keys retain their values; null removes an optional value. Defaults apply at item creation; folders receive no defaults and all fields are optional. The resulting item must satisfy its current content type. REST, bulk updates, Smart Folder actions and workflow activities use this same mutation path.

Item history is available at `GET /v1/items/{id}/revisions` and `GET /v1/items/{id}/revisions/{number}` with ordinary item-read permission and `item.read` scope. Each result includes its frozen schema, whether it is the current head, and the fields changed from the preceding revision. `$name` and `$keywords` identify system metadata. The list response uses `value` and `@odata.nextLink`; follow its `$skiptoken` continuation to page by revision number.

`POST /v1/items/{id}/revisions/{number}/restore` requires write permission and the item's current `If-Match`. It restores the historical content type (which must be attached) and metadata through current validation, clears current fields absent from the snapshot, and creates a new revision with ordinary indexing, publication and events. Removed fields remain removed. The current file blob is retained.

Items can change `content_type_id` through a resource PATCH or a bulk item update. The destination type must be attached to the collection. Shared field values survive, other values are pruned, and supplied values are checked against the destination type. Reclassification enforces required fields and validation rules without applying creation defaults. A new revision records the type change; existing publications retain their frozen type and content until republished.

`DELETE /v1/resources/{id}/content-types/{typeID}` detaches an unused collection attachment with `list.manage`, collection manage access and the current collection `If-Match`. The last attachment, types used by live items, and dependent saved views cannot be detached. Removing the default selects a remaining attachment by content-type ID. The catalog type, other collections and frozen history remain available. Deleted items whose type is detached require reattachment before restoration.
# Collection templates

GET `/v1/collection-templates` lists built-in Documents and Contacts templates and templates registered by modules. It requires `item.read`. POST `/v1/resources/{workspaceID}/children` with `name` and `template_key` creates a complete collection with settings, shared content types and saved views in one transaction. The caller needs workspace manage access, `item.write`, `list.manage` and `contentType.read`. A template determines the collection kind, folder policy, publishing and WebDAV settings; `content_type_ids` cannot be supplied with it.

Template content types have a stable organization provisioning identity. Reusing a template attaches the same live type and preserves curator customizations. Every item retains immutable revision history. Modules call `RegisterCollectionTemplate` before serving requests. Workspace schema recipes remain available for applying fields and rules to an existing collection.

Folders carry an attached `content_type_id`, selecting the collection default on creation. Their `values` accept the same field types, terms and keywords as items. Folder metadata edits are immediately visible even in publishing-enabled collections; folders cannot publish files or expose version history. Collection queries and saved views include folders, with indexed filters, sorting, grouping and selection. Smart Folders include them when `include_folders` is true, including taxonomy and content-type selectors. Reclassification prunes fields absent from the destination type, and a live folder prevents detaching its type. Delete removes live metadata indexes; restore rebuilds them from retained schema snapshots and requires the type to be attached.

Item and folder titles are trimmed after validation and allow 1024 UTF-16 code units. Non-BMP characters count as two units. Library filenames use the same length limit and exclude path separators, control characters and dot segments. Collections allow 64 nested folders, excluding workspace and collection levels; an item may sit below the deepest folder. Moves check the entire live subtree.
