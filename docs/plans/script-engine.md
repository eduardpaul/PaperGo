# Script workflow engine (plan)

Status: **spike.** The engine core, the SDK, the step journal and the in-process API path work on SQLite and PostgreSQL and are tested. Nothing serves or schedules script runs yet, and the JSON workflows and DBOS runner described in [runner.md](runner.md) are still in place. This branch replaces both before it merges; it never ships alongside them.

## Goal

Workflows are TypeScript (or JavaScript) scripts written against `@papergo/workflow`, a client generated from `api/openapi.json`. A script reads and writes PaperGo through the same REST API external clients use, acting as the workflow version's author. Long work, such as OCR, AI decisions or a human approval, is an API call that returns a pending operation, and `ctx.wait(operation)` unloads the run until it finishes. The engine runs on SQLite and PostgreSQL alike and replaces DBOS.

```ts
import { workflow, plain } from "@papergo/workflow";

export default workflow({
  async run(ctx, input: { list: string }) {
    const item = await ctx.api.v1.resources.byId(input.list).children.post({ kind: "item", name: "Invoice 7" });
    const bulk = await ctx.api.v1.resources.byId(input.list).bulkUpdate.post({ name: "Reviewed" });
    const done = await ctx.wait(bulk!);
    return { item: item?.id, updated: done.updated, result: plain(done.result) };
  },
});
```

## Execution model

A run executes in slices. Each slice creates a goja runtime, replays the script from the start and continues until it completes, fails or waits.

- **Steps.** Every API request, wait, clock reading and random value is a step in `workflow_steps`, numbered in the order the script makes it. On replay, a recorded step returns its recorded result instead of happening again. A step recorded for something else at the same position fails the run as nondeterministic.
- **Requests are exactly once.** `internal/scriptrun` runs a request through `httpapi.API.Loopback`, the `/v1` routes over a `dms.Service` bound to a transaction, and records the step with its response in that transaction. A 4xx response is recorded without the request's writes, so a replay sees the same refusal. A 5xx response is not recorded; the slice fails and the request runs again later.
- **Values travel with effects.** `Date`, `Math.random` and `crypto.randomUUID` are recorded steps, kept in memory until the next request or wait records them in its own transaction. A value nothing durable depended on is not stored.
- **Waits.** `ctx.wait(op)` records a wait step linked to the operations in `workflow_step_operations`. It is over at once when none is pending; otherwise the slice suspends. `operations.Repo.Save` and `Supersede` complete waiting steps whose operations have all finished, in the transaction that finishes the last one. The SDK then reads each operation through `GET /v1/operations/{id}`, so a script sees what an external client sees, and a failed or superseded operation throws `OperationError`. Waiting for several operations at once runs them in parallel and suspends once.
- **Suspension cannot be caught.** The engine interrupts the runtime, which JavaScript `try`, `catch` and `finally` do not observe, and discards it.
- **Limits.** A slice may run JavaScript for five seconds; time in host effects does not count. Outputs are limited to 256 KiB, responses to 1 MiB and the call stack to 4,096 frames.

## The SDK

`sdk/` is the `@papergo/workflow` package:

- `src/client/` is generated by Kiota 1.35.0 (`npm --prefix sdk run generate`). `scope.json` lists the paths scripts cannot call: identity, tokens, sign-in, organization, portability, storage, server events, `$batch` and workflow management. The generator leaves them out and the engine refuses them. The generator also strips the schema defaults Kiota writes for unset properties, because an update must not send fields the caller did not set.
- `src/adapter.ts` sends Kiota requests to the engine's host functions instead of the network. Kiota's fetch library is not used: its `fetch`, streams, timing and retry middleware cannot replay.
- `src/index.ts` defines `workflow()`, the context (`api`, `wait`, `log`), `OperationError` and `plain()` for Kiota untyped values such as an operation's result.
- `dist/sdk.js` (`npm --prefix sdk run build`) is the bundle Go embeds. The generated client and the bundle are committed so Go builds need no Node.

## Runtime

`internal/script` bundles a script with esbuild's Go API (one file; it may import only `@papergo/workflow`) and keeps compiled programs in an LRU cache keyed by bundle hash. The SDK program is compiled once and shared.

Each runtime provides ECMAScript and the SDK's host functions; the engine adds `TextEncoder` and `TextDecoder`, and the SDK defines `console`, which writes to the run's log. There is no `require`, `process`, `fetch`, timer or event loop: a bundle reaches the SDK through the `__papergoSdk` global the engine runs first. Binary request and response bodies cross the host as `ArrayBuffer`s. Without `Buffer` and `process`, Kiota takes its browser code path, which differs only for byte-array model fields; the client has none.

## Operations as the long-work contract

Every action a workflow waits for is an endpoint that returns `202 Accepted` with an `Operation` and its `Location`, like `bulk-update`, `search/reindex` and portability today. External clients poll `GET /v1/operations/{id}` or follow server events; scripts call `ctx.wait`. An operation's row, and its work, commit with the request, so in a script they are exactly once with the step. Results stay small: large outputs, such as recognized text, are stored in the domain and read through ordinary routes.

Operations run through `dms.RegisterOperationHandler`. `ExternalStep` handlers run outside the database writer, which suits OCR, embeddings, AI and PDF composition.

Reading text is the first such endpoint: `POST /v1/items/{id}/text` (`internal/documenttext`, see [OCR](../ocr.md)). A script reads a scan like this:

```ts
const started = await ctx.api.v1.items.byId(itemId).text.post({ ocr: "auto" });
const done = await ctx.wait(started!);
const text = await ctx.api.v1.items.byId(itemId).text.get();
```

## Performance

`go test ./internal/script -bench .` measures slices on an in-memory journal (Intel Xeon 2.1 GHz):

| Benchmark | Time | Allocated |
| --- | --- | --- |
| Compile the SDK, once per process | 28 ms | 10.8 MB |
| A runtime with the engine's globals | 0.02 ms | 0.02 MB |
| A runtime with the SDK loaded | 4.0 ms | 2.4 MB |
| `BenchmarkSlice`: a script that returns at once | 3.7 ms | 2.5 MB |
| `BenchmarkReplay`: replaying 100 recorded Kiota requests | 55 ms | 29 MB |
| `BenchmarkReplayHost`: the same 100 requests through the host directly | 5.9 ms | 3.1 MB |

- **What is cached.** The SDK is compiled once per process and shared by every runtime, and scripts are compiled once per bundle hash. goja cannot persist compiled programs or snapshot a loaded runtime, so each slice still runs the SDK's top-level code: about 4 ms. A pool of runtimes prepared ahead of demand would hide that latency, not save the CPU.
- **Kiota per call.** A replayed Kiota request costs about 0.5 ms; the engine's own share is about 15 µs. The bundle replaces `@opentelemetry/api` with a no-op tracer and `std-uritemplate` with an expander for Kiota's three template forms (`sdk/src/otel.ts`, `sdk/src/uritemplate.ts`), and JSON responses skip Kiota's byte round trip. Together these cut a slice by a quarter and a replayed request by over a third. What remains is Kiota's request objects and generated deserializers, which build a closure per model field for every response.
- **Replay grows with history.** Every resume replays every recorded step, so a run's total replay time grows with its number of waits times its number of steps. A run with 50 requests spread over five waits replays for under 0.1 s in all. Long loops should use bulk operations or child runs, not thousands of requests in one run.
- **Keep short waits warm.** The largest remaining saving is not replaying at all: a run waiting for a short operation, such as OCR of a page, can keep its runtime for a few seconds and continue in place when the wait is released, unloading only when the wait outlasts that window. This belongs in the scheduler.
- **Operations run one at a time.** `dms.RunOperations` is one sequential worker, so a 500-page OCR delays every operation queued behind it, including index builds and bulk updates. Text reading needs its own lane, with claims, before scripts depend on it at volume.

## Remaining work

1. **Run lifecycle.** Script definitions and immutable versions (source, bundle, hash, author), triggers declared by the script's export and extracted on save, run creation from domain events, manual starts and schedules, and run status.
2. **Scheduler.** Claim runnable runs with leases (`FOR UPDATE SKIP LOCKED` on PostgreSQL), execute slices, mark runs ready when a wait is released, recover runs a dead process held, cancel, retry from the failed step, and retention. `ctx.sleep` and wait timeouts need deadlines on wait steps.
3. **Operation endpoints.** Embeddings, AI decisions, PDF composition and task approvals as operation endpoints like text reading, with module scopes, per-caller admission limits, `Idempotency-Key` for external callers, cancellation, cancelling a run's operations with the run, and worker lanes so long work does not hold up short operations.
4. **Developer loop.** `papergo workflow dev` (watch, save a draft, start a run, stream logs and steps) and `papergo workflow test` (scripts' own tests on a disposable database with fake operations and a replay check that suspends after every step).
5. **Cutover.** Port the built-in workflows to scripts, then delete the JSON interpreter, the visual editor, the DBOS runner, its tables and `runner_step_results`, and their docs, in the same change.
6. **Contract fixes.** `BulkOperation` needs a discriminator; Kiota warns that it cannot deserialize it otherwise.
7. **Notices.** Ship the licence texts of the npm packages bundled into `sdk/dist/sdk.js` with release builds.

Known limits: goja has no heap limit, so a script can exhaust the process's memory; the time budget does not bound allocation. In-process requests rebuild the route table per request, and reads hold the writer on SQLite; both are acceptable for the spike and should be measured before the scheduler ships.
